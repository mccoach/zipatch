# 技术文档编写指南

> 职责：规定技术文档的分类、信息归属、编写、维护和审计方法，保证各有边界、不重不漏。
> 本指南只维护通用规则，不保存具体项目的需求、设计、路径清单、进度或执行历史。

## 1. 适用范围与使用边界

本指南供各项目共同使用。组件、库、工具及其他代码开发项目适用全部相关规则；知识库、来源研究及其他项目按实际职责选用文档类型，不照搬组件目录或接口章节。

统一的是信息职责、真实性和完整性，不是固定文件名、章节编号、目录层级或项目架构。本文中的文档名称表示职责，项目可以调整名称、合并职责或按模块拆分；合并后仍须分区维护，不能混淆信息类别。

项目不必另建本指南的专项版本。项目开发入口维护：
- 实际文档的类别、职责和唯一维护位置；
- 三份通用开发核心的真实入口；
- 项目最新状态和唯一当前行动位置。

已有职责映射可以直接引用，不建立第二份完整映射表。新增文件前先确定类别、独立职责、读者及与既有文件的边界；没有独立维护需要，不为形式完整新增文件。

本指南不替代以下通用开发核心：
- AI编程最高原则与最终态执行协议；
- AI自驱动人机协同开发SOP；
- Zipatch V3修改包协议规范。

核心可以位于项目内或共享目录，不为自包含复制大段正文，不在普通任务中独立修改核心或其副本。路径和链接只是入口，不代表正文已经读取或文件存在性已经核查。

## 2. 文档分类与唯一维护位置

| 类别 | 回答的问题 | 维护原则 |
| --- | --- | --- |
| A：现行说明 | 现在是什么、如何使用、遵守什么、有什么限制 | 保留当前有效规则，不叙述开发事件或实际任务安排 |
| B：累计历史 | 发生了什么、为何选择、如何变化、实际证明了什么 | 保存有长期价值的真实事件，通过追加表达新结论 |
| C：当前快照 | 最新状态是什么、当前做什么、如何进入或恢复 | 每个对象只保留最新有效状态，不累计逐轮经过 |

类别不必显式写在每份文档标题中，但项目开发入口必须能确定实际维护位置。

### 2.1 职责映射

| 文档职责 | 类别 | 唯一完整维护内容 |
| --- | --- | --- |
| README | A | 对外定位、实际环境与使用条件、安装、最短正确使用及必要限制 |
| 需求与验收目标 | A | 目标、长期范围、非目标、方向约束及需求级和项目级满足条件 |
| 架构设计 | A | 实现组织、职责、数据流、状态归属及明确标记的目标设计 |
| 接口契约 | A | 公共范围、跨模块通则及具体契约入口 |
| 模块说明 | A | 专属使用、签名、模型、字段、处理规则、失败及资源语义 |
| 外部依赖与依据 | A | 出处、适用版本、可信度、运行依赖及采用条件 |
| 测试与验证 | A | 标准验证方法、必要案例、命令及成功判据 |
| 本指南及其他规范、母版 | A | 文档组织、信息准入及执行规则，不代表业务能力 |
| 决策记录 | B | 重要选择、理由、变化与取代关系 |
| 验证记录 | B | 重要真实执行、失败修正、结果及证明范围 |
| 历史报告、原始执行证据 | B | 对应事件或观察，不代替现行说明 |
| 开发指导书等项目开发入口 | C | 项目摘要、导航、有效路线、最新状态及唯一当前行动 |
| 未决问题 | C | 活动的实质资料或裁决缺口 |

同一信息只在所属位置完整维护，其他位置仅保留面向本文件读者的必要摘要或明确引用。摘要不得成为第二份需要独立同步的规则、字段表、证据报告或任务清单。

### 2.2 关键边界

- 需求说明“满足什么”，测试说明“如何证明”，验证记录说明“实际证明了什么”。
- 需求级验收条件随需求维护；项目级验收引用需求编号，只补整体条件。
- 公共通则归接口契约，具体签名和模型归模块，不两处完整维护。
- 外部依据说明出处、可信度和适用性；模块说明自身如何采用、转换和落实。
- 历史决策归决策记录，最新有效规则同时进入相应现行说明。
- 当前行动归项目开发入口，实质资料或裁决缺口归未决问题，执行经过归历史。

## 3. 逐条判定与信息准入

以能独立表达事实的句子、列表项或表格单元格为判定单元。混合不同性质的信息先拆开，不能整段凭印象归类，也不能按关键词机械删除。

| 信息性质 | 判定依据 | 归属 |
| --- | --- | --- |
| 功能事实 | 当前接口、格式、字段、单位、异常、资源、依赖及能力边界 | 对应A类 |
| 规则及必要理由 | 不依赖某次事件，直接帮助使用、理解、维护或验证 | 对应A类 |
| 过程事件与执行证据 | 某次讨论、资料提供、交付、应用、运行、确认、失败、修正或发布 | 有长期价值时归B类 |
| 最新状态 | 最新结果、有效阻断及当前工程或使用影响 | 对应C类 |
| 行动与路线 | 下一动作、优先顺序、候选工作、进入或恢复条件、包处理 | 项目开发入口等C类 |

例如：“本次读取的文件大小”可以是模型语义；“本次修改已应用”是过程事件。“尚未实现”可以说明能力边界；“下一阶段实现”属于路线。长期职责和条件化维护方法属于A类，具体开发顺序和执行安排属于C类。

### 3.1 A类：保留当前有效说明

每条正文必须职责正确、当前有效，并对使用、理解、维护或验证有价值。

必须完整保留：
- 接口、类型、字段、单位、格式、默认值、失败和生命周期；
- 必要技术理由、公式、反例及完整使用示例；
- 来源、技术出处、适用版本、可信度及采用条件；
- 未实现能力、未知语义、支持范围及真实使用限制；
- 条件化使用、维护和验证步骤。

不得写入：
- 某轮增加、修改、交付、应用、修复或验收经过；
- 已交付、待应用、待反馈、本轮收口等包或过程状态；
- 实际运行日期、执行环境、通过数量、日志和人工确认；
- 样本验收摘要、工程失败处理经过及实际开发任务；
- 已废弃方案或历史实现作为现行规则的补充。

适用环境不等于某次执行环境，资料版本不等于交付版本，示例日期和公式反例不等于实际验收样本，不能一概删除数字或环境说明。

测试方法可以写执行什么、如何判定，不能写某次已经通过什么。接口索引可以区分已实现与目标接口，不能填写修改包状态或验收经过。

证据需要时提供明确入口，不复制验收摘要；链接不能代替本文件必须说明的专属语义和使用限制。历史支持的现行限制仍须在A类中明确表达。

### 3.2 B类：保留真实且有价值的历史

保留真实事件、当时结论、理由、失败修正和证明范围。当时的待反馈、未通过等状态可以作为历史事实保留，不因后来完成而追改。

新结果通过追加或明确取代关系表达，不覆盖旧证据。日期、版本、环境、数量、原因和结果必须有实际依据：
- 交付不等于应用；
- 静态审查不等于程序运行；
- 来源实验不等于组件工程验证；
- 工程检查不等于业务验收；
- 一次通过不等于全部环境、能力或历史覆盖。

没有实质增量不追加记录。普通编辑、完整日志和对话流水不自动归档。

### 3.3 C类：只维护最新有效快照

每个对象仅保留：
1. 一个最新有效状态；
2. 必要当前影响或限制；
3. 当前动作、进入条件或恢复条件；
4. 相关历史证据入口。

及时删除或更新失效等待、已解除阻断、被取代任务和过期路线；不复制逐轮经过、已完成动作清单、日志或验收摘要。

当前行动只有一个维护位置，默认在项目开发入口的当前行动节。路线可以保留有效顺序与进入条件，不另建第二份活动任务表。

未决问题只收需要资料或实质裁决的缺口，不收普通待实现功能、修改包执行等待或验证安排。快照可以说明最新检查未通过及其影响，具体失败经过和输出归B类。

## 4. 初始化、迁移与删除

### 4.1 初始化

初始化前确认项目根目录、实际文件、明确目标、源码和证据。未知文件不能被模板覆盖，不推断未提供的本机内容。

优先建立需求和开发入口，再补直接需要的说明。实际模块产生后建立模块文档，不为模板完整预建虚假能力页面、历史条目或无需求框架。

没有实现时可以写目标设计，但必须明确未实现，不发布未确定API、空壳签名或伪造使用命令。母版和占位内容不表示已经核查且没有问题、决策或证据，也不作为实际能力导航。

### 4.2 迁移与删除

| 情况 | 处理 |
| --- | --- |
| 错误位置的过程信息已有正确记录 | 删除副本，不重复追加 |
| 唯一且有长期价值的过程信息 | 先迁入正确B类，再删除原位置 |
| 唯一但仅普通流水 | 直接删除，不无限归档 |
| 同一条混合规则与事件 | 拆开，保留有效规则，事件按价值删除或迁移 |
| 历史支持当前限制 | 保留限制并引用证据，不复制经过 |
| 归属不明确 | 先判断性质和必要性，不随意新建文件 |

每项必要迁移须能说明原位置、目标和保留理由；已有正确记录时不重复迁入。不能以避免丢信息为由归档全部过程，也不能为精简丢失唯一契约和重要证据。

清理A类时，不顺带重写、归并或清理B类历史；必要的唯一信息迁移除外，改动控制在实际需要范围。历史删除或追改必须有明确授权，不能仅因与最新状态不同而修改旧记录。

记录无法完整迁入时，明确尚未整理并保留真实入口，不将其写成没有历史。

实质问题解决后，先将必要规则、选择和证据归位，再移出活动问题；不长期维护已解决列表作为第二份历史。

## 5. 模块契约与外部依据

### 5.1 模块说明完整性

模块说明应完整定义实际使用所需的专属契约。以下项目按实际能力适用，不为不适用内容编造语义：
- 用途、推荐入口、前置条件和非目标；
- 必要导入、参数和质量检查齐备的使用示例；
- 输入输出、默认值、校验规则和执行时机；
- 存储字段与派生属性、类型、单位、空值及语义依据；
- 顺序、重复、计数、部分结果和覆盖行为；
- 错误、关闭、超时、取消、并发、生命周期与副作用；
- 精确处理规则、必要理由及维护限制；
- 独有回归案例与标准验证入口。

公共通则可以引用，但不能以“只写差异”为理由遗漏关键使用语义；引用后，读者仍须能确定模块专属参数、默认值、质量及失败规则。

不强制固定章节数，不按读者建立多份相同契约。内部装配和实验工具不自动成为公共API。目标结构与当前实现分开，不由模板要求预建层级、注册表、状态机、插件或空适配模块。

### 5.2 外部依据与独立来源

存在外部知识库、来源规范或上游资料时：
- 外部依据维护来源事实、出处、可信度、适用版本和采用条件；
- 组件维护自身实际采用、转换、校验和落实的规则；
- 比较差异时依据实际证据与风险，不机械照搬任何一方；
- 不全文复制上游资料，也不因禁止复制而省略必要精确格式；
- 来源实验与组件工程证据分别归属，必要时互链，不重复维护长报告。

研究、采集、回放和诊断工具须有明确代码归属。已确认的运行能力避免在工具中复制第二实现，实验假设不混入正式接口。源码分区、部署和项目数量由实际职责决定，不由文档布局决定。

## 6. 维护触发与工程边界

| 变化 | 更新位置 |
| --- | --- |
| 需求、范围或满足条件变化 | 需求与验收目标 |
| 组织、职责、数据流或状态归属变化 | 架构设计 |
| 公共行为或专属契约变化 | 接口契约及受影响模块说明 |
| 外部规则、适用性或依赖变化 | 外部依赖与依据及受影响的采用规则 |
| 验证方法或成功判据变化 | 测试与验证 |
| 最新状态、路线或当前行动变化 | 项目开发入口 |
| 实质资料或裁决缺口变化 | 未决问题 |
| 重要真实选择或执行增量 | 对应决策记录或验证记录 |

按实际影响更新，不每轮同步全部文件，不为普通编辑生成历史记录。跨文件变更只同步受影响内容，不制造重复维护。

契约变更遵守通用核心的最终态要求：同步所有受影响调用，不保留错误别名、旧兼容、双轨或隐藏fallback；必要一次性迁移不进入正式兼容链路。外部适用版本不等于保留项目旧版实现。

指南迭代只提取共性规则，不将单项目字段、偶发故障、临时路径或执行安排扩成通用要求。指南变化后核对实际影响，不自动批量重写全部项目成果；发生规范冲突先核对相关正文，不让项目自定规则覆盖通用核心。

## 7. 路径、安全与接续

一般导航采用相对路径；实际定位、执行和复现使用真实路径，并说明必要环境。示例或母版中的默认路径须在项目使用时核对，不原样当作事实。

不虚构核心、源码、工具、日志、数据或资料位置。导航必须有真实或明确预定的位置依据，预定位置不能冒充已存在文件。链接检查不能替代正文读取。

不写入凭据、敏感个人数据或未经授权的来源。示例与日志脱敏，必要原始证据受控保存并提供适当入口。

同一对话沿用已提供且仍有效的材料；原样完整应用确认可以建立载荷基线，手工修改、格式化或其他操作改变文件后，核对受影响的最新正文。

新对话提供核心、开发入口及任务直接需要的素材，不默认全量装载历史。多个项目协同使用一份去重素材清单，资料可以合并提交，文件修改仍按真实项目根目录边界交付。

下一轮提示词、应用步骤和结果要求由回复提供，不默认创建永久提示词、固定上下文或交接台账。实际当前行动变化更新其唯一快照位置。

涉及文件修改使用Zipatch V3，并遵守核心授权和执行要求。

## 8. 审计与交付判据

审计按语义逐条执行，以第2至第7节为依据。重点检查：
- 信息是否归入正确类别，混合信息是否拆开；
- 唯一维护位置是否明确，摘要和引用是否形成第二套完整内容；
- A类是否仅保留当前有效说明，B类是否真实且受到保护，C类是否只有最新有效状态；
- 必要迁移是否有来源、目标和理由，唯一契约与重要证据是否保全；
- 接口、字段、单位、失败、资源和限制是否完整，目标与实际实现是否分开；
- 导航、路径、示例和命令是否有依据并适用于所述环境；
- 是否存在虚假能力、空壳承诺、敏感信息或未经授权来源；
- 是否借文档整理启动无关代码修复、数据清理、架构扩张或历史治理。

关键词搜索、链接检查和排版检查只能辅助定位，不能代替语义判断；缩写全文、减少字数或统一格式不代表审计完成。

交付只报告影响使用、决策和应用的重要结果，以及尚未核查的边界，不机械打印完整检查表。

文档审查不等于本机应用、程序运行或业务验收。对实际完成、验证范围和剩余限制的表述，必须与所掌握的真实证据一致。
